## ⚡ 30 秒看懂它和别的项目有什么不一样

榜单上的省钱类项目帮你算**下一单怎么买**，热量类项目帮你算**这一餐吃多少**。
我们做的事完全不同：**把已经发生的历史订单，一单不落地重新点一遍。**

| | 省钱类 | 热量类 | 年度总结类 | **麦门 Diff** |
|---|---|---|---|---|
| **时态** | 现在 | 现在 | 过去 · 聚合 | **过去 · 反事实** |
| **在问什么** | 我该买什么 | 我该吃多少 | 我做了什么 | **我本该做什么** |
| **作用对象** | 未来一单 | 未来一单 | 历史总计 | **历史逐单重算** |
| **输出** | 方案文本 | 方案文本 | 人格标签 | **差额 + 平行对照** |
| **可验证性** | 弱 | 弱 | 弱 | **强 —— 每一单都能复算** |

**一句话**：省钱类是「下单前的军师」，年度总结是「年终的司仪」，我们是 **「逐单复盘的教练」** ——
用的不是建议，是**你自己的订单**。

> 为什么没人做这个？因为大多数人只敢对"未来"给建议。对已经花掉的钱做复盘，
> 需要一套**约束足够严谨**的算法 —— 否则就是在指手画脚。见下一节。

## 🔒 三条自我约束（这是它敢叫「重开」的原因）

这不是"教你省钱"的工具。三条硬约束决定了它对用户的态度：

### ① 约束天花板 = **这一单自己**

```text
预算上限 = 该单的实付金额      → 不劝你少花
热量上限 = 该单的实际热量      → 不劝你少吃
蛋白质下限 = 该单的实际蛋白    → 不让营养变差
```

如果像省钱类那样解"最小化价格"，必然推出"什么都别点最省"；
像热量类那样解"最小化热量"，必然推出"只喝零度可乐最轻"。

我们把上限**锁定为该单原有的值**，只问一句话：

> **「同样的钱、同样的热量，能不能吃得更好？」**

因此输出永远是**同条件更优解**，不是"你该少花"。

**一个自洽性**：因为预算上限 = 该单实付，所以 `Δcost ≥ 0` 数学上必然成立 —— 不需要任何裁剪。

### ② 结构保留 —— 不做"把饮料删掉"式的伪优化

第一版跑出来的建议是这样的：

```diff
- 猪柳蛋麦满分 · 鲜煮咖啡    ¥28
+ 猪柳蛋麦满分              ¥16      ← 省了 ¥12，但你的咖啡没了
```

**这不叫更优解，这叫少给东西。** 所以求解器先加了品类约束：
**原单有饮料，重开就必须也有饮料。**

```diff
- 猪柳蛋麦满分 · 鲜煮咖啡    ¥28
+ 吉士蛋麦满分 · 鲜煮咖啡    ¥27      ← 结构不变，品类齐全
```

用户想喝咖啡，但未必要喝**这一杯**咖啡 —— 换一杯更便宜的是优化；
直接把咖啡取消，是耍流氓。

**但"保留品类"还不够。** 换成真实菜单后又发现：原单是「1 个汉堡 + 2 份小食 + 1 杯饮料」，
重开之后变成「1 个汉堡 + 1 份小食 + 1 杯饮料」也算"品类齐全" —— 可你的小食少了一份。
所以约束再升一级，从「品类集合」变成「**品类 + 份数**」：

```text
原单结构 {小食: 2, 饮品: 1, 汉堡: 1}
  → 重开方案必须满足  小食 ≥ 2 且 饮品 ≥ 1 且 汉堡 ≥ 1
```

效果是把省钱数字从 ¥459 压到 ¥371（−19%），**换来的是每一条建议都读得通**。
这个取舍很值：一个看起来像"系统在乱点"的数字，没人会信。

### ③ 口径对齐 —— 让"重开价"和"实付"可比

订单实付里含优惠，而菜单标的是原价。拿实付去卡原价菜单，会得到一堆"无解"。

所以我们按**该单自身的折扣系数缩放菜单价格**，等价于假设：

> 「那天的优惠力度不变，换个点法会怎样。」

实测这一步让可解率从 45% 提升到 **100%**。

## ✨ 五大模块

### 1 · ⏪ 重开橱窗

一单一单左右对照，左边是你实际点的，右边是同等条件下的更优解。

```diff
  #01  2026-04-06 20:12 · 杭州武林广场店
- 麦辣鸡腿汉堡 · 薯条 · 可乐 · 薄皮焦香V翅
+ 那么大鸡排（椒盐风味） · 麦香鸡 · 圆筒冰淇淋 · 优品豆浆
  ¥54.44 → ¥40.28    省 ¥14.16 · 少 64 kcal · 4 件对 4 件
```

### 2 · 💸 差额账簿

| 指标 | 示例值 |
|---|---|
| 可节省空间 | **¥371**（占全年 14.0%） |
| 可减热量 | 5,162 kcal |
| 蛋白净变化 | +161 g |
| 单均可省 | ¥5.02 |
| 重开潜力 | 35 / 100 |
| 有重开空间的单 | 61 / 74 |
| 已是最优的单 | 13 / 74 |

再按时段、渠道两个维度归因 —— 实测**午餐单**（20.5%）与**晚餐单**（18.9%）的可节省率最高，
早餐单只有 6.0% —— 早上你本来就点得挺克制。

### 3 · 🧭 三条重开路线

**约束完全相同，只有目标函数不同** —— 所以结果天然可对照。
同一段历史，你想把它重开成什么样？

| 路线 | 目标函数 | 可省金额 | 可减热量 | 蛋白净变化 |
|---|---|---:|---:|---:|
| **省钱向**（默认） | 价格最低 | **¥371** | 5,162 kcal | +161 g |
| 扎实向 | 蛋白质最高 | ¥73 | 2,959 kcal | **+493 g** |
| 轻负担向 | 热量最低 | ¥103 | **12,268 kcal** | +103 g |

> 这张表本身就是产品价值：**"省钱"和"吃得扎实"是两件事** ——
> 扎实向只省得下 ¥73，却能在同样的钱和热量里多换 **493 g** 蛋白质。
> 市面上所有工具都只给你一个答案，我们给你三个，并告诉你代价是什么。

把重开后的订单集重新送进人格引擎，再和现实做一次并排：

| | 现实宇宙 | 平行宇宙 |

## 🏗️ 架构与工作流

```text
┌──────────────────┐  ① 采集  ┌──────────────────┐
│ scripts/collect  │ ───────▶ │ .mcd-diff/       │
│ 麦当劳 MCP 客户端 │ JSON 落盘 │ raw.json+menu.json│
└──────────────────┘          └────────┬─────────┘
        ▲ 也可由 WorkBuddy Agent 编排 │ ② 本地计算（纯标准库，无网络）
        │                              ▼
        │     ┌──────────────────────────────────────────────────┐
        │     │ metrics  → 原有统计（时段 / 渠道 / 人格特征）        │
        │     │ menu     → 菜单与营养表（含 category）             │
        │     │ solver   → 双约束求解 + **结构保留**（品类 + 份数）  │
        │     │ regret   → **逐单重开 → Δcost / Δkcal / Δprotein** │
        │     │ persona  → 现实人格 vs 平行宇宙人格                 │
        │     └───────────────────────┬──────────────────────────┘
        │                             │ ③ 渲染
        │                             ▼
        │              📄 麦门 Diff 报告（自包含 HTML / MD / JSON）
        └── 全程只读：7 个交易类 Tool 被 assert_readonly() 硬拦截
```

**设计原则**

- **采集与计算分离**：MCP 只负责取数落盘；计算层零网络、零依赖、可单测、可复现。
- **自带 MCP 客户端**：`scripts/collect.py` 用标准库实现了 Streamable HTTP，
  所以项目**不依赖 WorkBuddy 也能独立跑通** —— 换任何 MCP Client 都能用。
- **Agent 是编排者，不是计算器**：LLM 调用工具与叙述；确定性算法负责差额与求解。
- **只读边界**：全程不调用任何交易类工具，`assert_readonly()` 硬拦截。
- **默认离线**：产物是一个可双击打开的 HTML，不联网、不上传。

### 性能：从 66 秒到 4.9 秒

真实菜单比示例菜单大得多 —— 一餐 ≤ 4 件时组合数是 O(N⁴)，
41 项菜单就有 **112,791 种组合**；74 单 × 4 条路线 = 296 次求解，
朴素全枚举要跑 **66 秒**。

做了三件事把它压到 **4.9 秒**（结果逐位相同）：

| 优化 | 做法 |
|---|---|
| **组合表只算一次** | 枚举与各项求和全部预计算，按菜单指纹缓存；整轮重开只构建一次 |
| **按目标预排序，首个可行即最优** | 排序键与平手规则完全一致，扫到第一个满足约束的组合就能返回（实测几百次比较） |
| **价格系数不落地成菜单** | 折扣系数做成 `Constraints.price_factor`，而不是复制一张缩放后的菜单 —— **正数缩放不改变排序**，同一张组合表对所有订单都成立 |

**全枚举即精确最优，零启发式、完全确定性、可单测。**
41 项真实菜单 × 每餐 ≤ 4 件 = **112,791 种组合**，
枚举 + 三种目标各排一遍，整张组合表构建一次只要 **0.9 秒**；
`MAX_COMBO_SIZE` 再往上加一档，组合数会从 11 万跳到 86 万，性价比急剧下降，
而 4 件已经覆盖了绝大多数真实点餐。

## 🚀 快速开始

### 0. 前置条件

- Python **3.10+**（仅使用标准库）
- 麦当劳 MCP Token（<https://open.mcd.cn/mcp> → 手机号登录 → 控制台 → 激活）
- 支持 **Streamable HTTP** 的 MCP Client（推荐 **WorkBuddy**）

### 1. 克隆仓库

```bash
git clone https://github.com/weixiao121/mcd-diff.git
cd mcd-diff
```

### 2. 配置 MCP（以 WorkBuddy 为例）

左侧【专家·技能·连接器】→【连接器】→【自定义连接器】→【配置 MCP】，
粘贴 [`mcp-config.example.json`](mcp-config.example.json)，把 `${MCD_MCP_TOKEN}` 换成真实 Token →【保存】→ 启用 `mcd-mcp`。

本地运行时用环境变量注入（**不要把 Token 写进任何被提交的文件**）：

```bash
export MCD_MCP_TOKEN="your-token-here"     # Windows PowerShell: $env:MCD_MCP_TOKEN="..."
```

### 3. 采集真实数据

**方式 A：在 WorkBuddy 里说人话**（Skill 定义见 [`SKILL.md`](SKILL.md)）

把本仓库作为 Skill 目录加载后，直接说人话即可：

```text
你：帮我把这一年的麦当劳订单跑一遍 diff
AI：（依次调用 order-list / query-order / query-meals / list-nutrition-foods /
     query-my-account / mall-order-list）
    → 写入 .mcd-diff/raw.json
    → 运行 python -m mcd_diff diff --input .mcd-diff/raw.json --out diff-report.html
🎉 报告已生成 → 打开 diff-report.html
```

也支持「预算 + 热量」的双上限提问，走独立的求解流程：

```text
你：预算 35 元、800 kcal 以内，怎么点最扎实？
AI：python -m mcd_diff solve --budget 35 --kcal 800
    → 给出 A 省钱优先 / B 热量优先 / C 双约束 三方案对照
```

**方式 B：命令行直接采集**（不依赖 WorkBuddy，自带 MCP 客户端）

[`scripts/collect.py`](scripts/collect.py) 里内置了一个**标准库 MCP 客户端**
—— 用 `urllib.request` 手写 `initialize` → `tools/call`，兼容裸 JSON 与 SSE 两种响应，
**零第三方依赖**。跑完即得到求解器要的两个文件：

```bash
export MCD_MCP_TOKEN="your-token-here"            # 也可直接用 --token 传入

python scripts/collect.py                          # → .mcd-diff/raw.json + .mcd-diff/menu.json
python scripts/collect.py --menu data/menu.json    # 顺便刷新仓库里的菜单快照
```

Token 解析顺序：`--token` > 环境变量 `MCD_MCP_TOKEN` > WorkBuddy 的 `mcp.json`。

仓库里的 [`data/menu.json`](data/menu.json) 就是这个脚本拉下来的 ——
**41 项真实在售单品，真价格、真营养，未做人工调整**（多时段探测后合并：
早餐品项只有清晨那轮才拉得到）。

### 4. 不想连 MCP？先跑示例看看效果

```bash
python examples/generate_sample_data.py            # 生成 74 单脱敏虚构数据
python scripts/analyze.py diff \
  --input examples/sample_raw.json \
  --out   examples/sample_diff.html \
  --mode  thrift
```

示例订单是**程序生成的虚构数据**（组合自上面那份真实菜单），产物预览：
[`examples/sample_diff.html`](examples/sample_diff.html) ｜ [`examples/sample_diff.md`](examples/sample_diff.md)

### 5. CLI 用法

```bash
# 生成重开报告（--mode 可选 thrift 省钱向 / balanced 扎实向 / lean 轻负担向）
python -m mcd_diff diff --input raw.json --out report.html --format html|md|json --mode thrift

# 只做一次双约束求解（仍是纯本地计算）
python -m mcd_diff solve --budget 35 --kcal 800 [--protein 15] [--sodium 2000]
```

## ❓ FAQ

**Q：会不会泄露我的隐私？**
不会。采集数据只写入本地 `.mcd-diff/raw.json`，报告离线生成；Token 只从环境变量读取，仓库内配置文件**只有占位符**。

**Q：它会不会替我下单？**
不会。「重开」是**纯本地枚举计算**，只输出建议文本；代码中有 `assert_readonly()` 显式拦截所有交易类工具。

**Q：为什么差额一定要 ≥ 0？**
因为求解器的预算上限就是**该单自己的实付金额**，重开价不可能超过它 —— 这是数学保证，不是事后裁剪。

**Q：为什么不让它把饮料优化掉？那样不是省更多吗？**
那样省的是"**你少喝了杯咖啡**"的钱，不是"你被多收"的钱。我们加了**结构保留**约束
—— 不只要品类齐全，还要**份数对得上**（原单「1 汉堡 + 2 小食 + 1 饮品」，
重开也必须是小食两份），只做结构不变的等效替换。

**Q：优惠券怎么处理？**
v1.0 用该单自身的折扣系数 `price_factor = 实付 ÷ 菜单原价` 缩放菜单，
保证两边口径一致（等价于"优惠力度不变，换个点法"）。它落在约束层而不是真去改菜单价格 ——
**正数缩放不改变排序**，所以同一张组合表对所有订单都成立。
更精确的**券后重开**（直接吃 `query-store-coupons` 的真实券面）在 v1.2。

**Q：为什么用全枚举而不是动态规划？**
菜单 41 项、一餐 ≤ 4 件，全集 112,791 种组合 —— 全枚举即可得到**精确最优解**，
枚举一遍不到 1 秒，代码更短、更易审计，还能直接支持结构保留、钠上限等任意组合条件。
